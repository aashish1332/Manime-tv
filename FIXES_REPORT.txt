SECTION 00006 - PROVIDER TAGS ON EVERY CARD, IMMEDIATELY

What was wrong: SourceBadges() returned early unless Anime.sourcesResolved
was true, and that flag is only set once ALL THREE site catalogues are in
memory. On a cold start the catalogues do not even begin until the 10s
background settle, so posters painted with NO tags, and the tags only
appeared after the catalogues landed and the feed re-merged - roughly 20s
in the good case, and up to the 60s grace when one site was slow or down.
A cached feed from disk was gated the same way, so the very first frame
of a launch could also be bare.

Fix: the badges are drawn from what the merge already matched, always.
  - AnimeCard.SourceBadges no longer returns early; ADH / AD / T4A / DDA
    render together with the poster, in that priority order (blue, green,
    purple, orange), for every card that has at least one source.
  - A catalogue landing still invalidates and re-merges the feed, so a
    card whose source set was only completed by the full catalogue gains
    its extra badge then - one merge, not one badge at a time.
  - That re-merge now settles for 1.5s instead of 6s (BADGE_REFIRE_MS),
    because its only job is completing source sets; the grace release
    fires immediately (delay 0) for the same reason.

Nothing else about the card changed: the same four labels, the same
colors, the same position (bottom-left), the same 9sp size.

00004A. THE POST-FEED BACKGROUND STORM (the real stutter)
  startBackgroundWork() fired the moment the first feed landed: the
  three full catalogs immediately, the ~600-page slug sweep behind the
  ADH one, and the title sweep 4s later. That is precisely when the grid
  is binding ~30 posters and the viewer starts moving the focus ring -
  and every one of those jobs is an HTML fetch plus a Jsoup parse on the
  same cores the renderer needs.
  Now: 10s dead time after the first feed (BACKGROUND_SETTLE_MS), then
  InteractionGate.awaitQuiet(2s) before the catalogs start, and the slug
  sweep waits for quiet AGAIN before its first page. The title sweep
  moved from 4s to 30s. Sweeps breathe 250ms between pages (was 120ms)
  and the bulk lane dropped to 4 requests / 2 per host (was 6/3).
  The feed re-merge that lands after a catalog is now debounced 6s (was
  2.5s) and also waits for the app to be idle - it swaps the whole grid,
  so it must not land mid-scroll.
  InteractionGate gained awaitQuiet(quietMs): it suspends until nothing
  has been in flight for that long, bounded at 90s so a sweep can never
  be parked forever.

00004B. GDFLIX - VERIFIED LIVE, AND MOVED BACK INTO THE FAST PASS
  End-to-end test against a real ADH link (gdflix.vip/file/<id>), done
  with curl only, no browser:

         header x-token: new10.gdflix.io
         -> {"error":false,"url":"https://video-downloads.googleusercontent…"}
                                 in 0.9s
  i.e. the plain-HTTP protocol in gdflixInstant() is correct today.
  Two changes made it actually get used:
   - autoResolve() used to hold GDFlix back for a browser-unlock round
     (isGatedHoster). GDFlix is not gated any more, so every hub now gets
     the fast plain-HTTP pass first and the browser is only a second
     chance.
   - the instant stage's slice went 8s -> 12s (the 3.7s page fetch was
     being killed on slow boxes and then paid for twice by the fallback),
     plain HTTP 10s -> 8s.

00004C. FILEPRESS - THE ORIGIN IS GONE, SO FAIL IN A SECOND
  Live: fpgo.xyz and filepress.baby both 301 to new4.filepress.lat, and
  that host blackholes connections (DNS answers 49.44.79.236, every
  connect stalls 20s+, HTTP and HTTPS, IPv4 and IPv6). This is a

  filepressFetch() now resolves the alias with a 6s cap, remembers the
  origin for 30 min, and marks FilePress DOWN for 5 min on a connection
  failure; resolve() then returns null immediately, so the player moves
  to the next server instead of sitting on the spinner. Repeat picks in
  the same session skip the alias hop entirely.

00004D. TOONWORLD4ALL - NO QR, NO ADS, SAME SPEED
  Verified with curl against a real episode (blue-box-2x6):
    episode page         200, 29KB, 1.4s
    /redirect/<token>    200, 13.9KB, 1.3s
    __PROPS__ inside it:  "domain":"https://gdflix.dev/file/" +
                          "hidden":"o97e5vr7jwwitka"  (no ad, no QR)
  That is exactly the path FileHostResolver already takes (redirect ->
  target -> right hoster resolver), and the target resolves with the
  GDFlix flow above. For comparison, animedubhindi's adhlinks episode
  page answered in 1.65s and its home page in 2.0s, ToonWorld's home in
  2.5s - the same class of latency, so speed is not the issue.
  A MEGA row is a download-only host and is still filtered out of the
  server list, so it can never open the QR sheet.
  The hint that told viewers to go solve 3 ads on their phone is gone:
  it now points at the HubCloud/GDFlix rows instead.

00004E. HOW VEGA-TV DOES PROVIDERS (read-only, nothing touched)
  Its provider layer is a JS sandbox: provider bundles run in one hidden
  WebView (cheerio bundled, fetch/axios/kv shims), and every network
  call goes through a native OkHttp bridge (ProviderHttp) because the
  WebView page is CORS-bound. Cookies live in the process-wide
  CookieManager shared with a visible WebView that solves Cloudflare
  challenges, and streams are handed to the player WITH that jar as a
  Cookie header - the same idea FileHostResolver already uses via
  browser.cookiesFor(). It also rate-limits per host and serialises
  invokes. Nothing in that design applies to this app's fixed set of
  four sources; the reusable parts (shared cookie jar, stream headers,
  one invoke at a time) are already present here.

00004F. A DOWN HOST NO LONGER HOLDS ITS RESOLVE BATCH
  Once every hub entered the fast pass, a dead FilePress row could cost a
  batch its whole wall clock: raceForStream() awaits EVERY member, so two
  healthy servers answering in ~1s still waited on the dead one.
  FileHostResolver.isDown(hoster) now exposes the 5-minute verdict, and
  raceForStream() drops those rows BEFORE making a request (empty result
  -> next batch, no delay). The browser-unlock pass skips them too, so no
  unlock round is spent on a host that cannot answer.
  resolve() also refuses a down-marked host at its first line, whatever
  the label on the link says.
  Removed dead fallbacks: the whole api.filebee.xyz stage
  (filebeePlainHttp + FILEBEE_METHODS, ~6s of guaranteed waiting, the
  host does not answer at all) and its unused helpers. FilePress now has
  exactly one delivery path: the alias's own `/api` proxy.
  The guard in resolve() repeats none of this logic: isDown(hoster) is the
  single check at the top of the call, and the duplicate a few lines
  further in (inside the FilePress branch) is gone.

SECTION 00003 — 2026-11-24 SESSION #8 (startup stutter, spinner,

Reported: app still lags/stutters after opening (while refreshing);
GDFlix says "no stream" 2-3s after picking it; FilePress stuck on

00003A. WHY THE SPINNER NEVER ROTATED
  All four spinners were Material3 CircularProgressIndicator, which
  animates through rememberInfiniteTransition. Compose scales that by
  the platform MotionDurationScale; on boxes with "Animator duration
  scale" = 0 (common on Android TV, and a developer setting) the factor
  is 0 and an INFINITE transition does not advance at all. The arc was
  drawn and then frozen — exactly the report.
  New ui/common/Spinner.kt draws a 270-degree arc whose angle is
  computed from the frame clock's timestamps (withFrameNanos), which the
  duration scale does not touch. It suspends between frames, so it costs
  nothing in the background and cannot drift on a busy device.
  Replaced all four usages: LoadingScreen, sidebar refresh, search, and
  the player's loading + buffering overlay.

00003B. GDFLIX "no stream" AFTER 2-3s — THE BUDGET WAS EATEN
  The GDFlix branch ran 20s (instant path) + 30s (plain HTTP) + a
  3 x 120s browser retry loop. The caller gives 45s (MANUAL_RESOLVE_MS),
  so the outer timeout killed the resolve during the browser stage — the
  only stage that can beat Cloudflare. GDFlix therefore could not
  succeed, and the failure message showed up almost immediately.
  Now every stage gets a slice of the caller's budget (8s instant, 10s
  plain, the remainder to ONE browser capture capped at BROWSER_CAP_MS)
  and checks the remaining time before starting. The 3 x 120s loop is
  gone; it could never finish inside any budget.

00003C. FILEPRESS "stuck on loading" — THE BROWSER OPENED THE WRONG PAGE
  The resolve identifies the real FilePress page (filepressPageUrl) and
  used it for the API calls, but the browser click-capture step below
  still opened the ORIGINAL pageUrl — the adhlinks/interstitial page.
  A page with no download button can only time out, so the player sat on
  "loading" until the caller's timeout fired.
  browserPageUrl now carries the identified page into the browser step,
  and the two API stages are budget-capped (12s / 10s) instead of the
  fixed 20s + 25s that could exceed the caller's budget on their own.

00003D. STARTUP STUTTER
  Two concrete causes removed:
  1. App.onCreate blocked the MAIN THREAD with runBlocking { settings
     .ddaBase() }. The first DataStore read is disk I/O and it ran before
     the first frame. It now happens inside the launch coroutine, ahead
     of the first request — WpService resolves Api.HOST per call, so
     nothing needs it earlier.
  2. HomeViewModel published a new UiState on every load and re-merge.
     The first seconds after launch produce the cached feed, the network
     feed, and a re-merge each time a source catalog lands; every one of
     those recomposed the whole grid and re-bound ~30 posters in Coil.
     publish() now compares structurally and skips identical feeds
     (HomeFeed/Anime are data classes).
  NOT measured on a device — there is no adb here. These are code-level
  causes removed, not a measured speedup.

00003E. HINGLISH REMOVED
  User-facing strings:
    "Is page pe kuch nahi mila."  ->  "No anime found on that page."
    "... se stream nahi mila - dusra server chuno."  ->
      "... returned no stream - pick another server."
  Hinglish comments translated in PlayerViewModel, FileHostBrowser,
  TwUnlockHolder, PlayerMenu and AnimeRepository. Three log lines that
  rendered as mojibake in the on-screen server log now use ASCII.

00003F. VERIFY
  OK  :app:compileDebugKotlin BUILD SUCCESSFUL
  OK  :app:searchCheck — 19/19 checks still pass
  NAHI Device-level: no adb and no TV box on this machine. Spinner
       rotation, GDFlix and FilePress resolution were NOT exercised at
       runtime; they are fixed from the code paths, not from a trace.

00002A. PEHLE KYA GALAT THA — ACCURACY
  Chaaron sites WordPress search use karte hain, aur WP ka `search`
  parameter TITLE ke saath post ka CONTENT bhi match karta hai. Isliye
  ek show dhoondhne par aise anime bhi aate the jinke synopsis me wo
  shabd hai, aur result RECENCY order me aata tha — sahi show kabhi
  teesre-chauthe card par. Local catalog scan bhi poore query ka
  substring (`contains`) dekhta tha, isliye:
    "slime reincarnated" -> 0 (word order ulta)
    "slimee" (typo)      -> 0
  code ka comment typo coverage ka dawa karta tha; tha hi nahi.

00002B. AB KYA HOTA HAI — RANKING (rankSearch)
  Merge ke baad har card ko uske TITLE par tier milta hai:
    5 = exact        ("naruto" == "Naruto")
    4 = starts with
    3 = contains
    2 = saare query words title me, kisi bhi order me
    1 = ek typo door (insert/delete/substitute/swap, 4+ letters)
    0 = sirf content match
  Tier 5..1 order karte hain, tie par recency (latestEpisodeAt /
  updatedAt / publishedAt). Tier 0 tabhi dikhta hai jab koi bhi
  title match na mile — recall chupchaap nahi girti, sirf tab demote
  hoti hai jab asli title match maujood ho.

00002C. CATALOG SCAN AB TITLE-AWARE
  adhCatalog / adCatalog / twCatalog memory me hote hain, to ab wahi
  rules un par bhi chalte hain (network zero). Yahi hissa tab bhi
  kaam karta hai jab site ka apna search down ho, rate-limited ho, ya
  uske 20 slots content matches se bhar jayein. 3 se chhote query par
  scan nahi chalta.
  TYPO PASS GATED HAI: pehle sirf strict tiers (exact / prefix /
  contains / word-order) check hote hain — catalog par, network
  results par, aur DDA results par. Agar kuch bhi strict match na mile
  (aur query 4+ harf ki ho) TABHI poora catalog fuzzy scan hota hai.
  Yaani jis key press ka jawab pehle se maujood hai wo low-RAM box par
